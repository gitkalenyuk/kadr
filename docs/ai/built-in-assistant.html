The built-in AI assistant

Kadr has an AI assistant inside the editor (the AI button, Ctrl+Shift+A). It drives Kadr through the same command registry as every other agent, with two kinds of backends: coding-agent CLIs installed on the PC, and a built-in agent loop over LLM APIs. This page explains how it works — useful if you are an agent launched by it, if you script it over the API, or if you add commands that it must treat with care. How people use it is in the user guide.

Two backends

Meta-tools of the API backend

ToolWhat it does
kadr_find_commandsSearches the registry by keywords or category (no arguments = the categories); returns names with one-line summaries.
kadr_describeFull documentation of a command: parameters, units, ranges, examples — the same text as the command reference.
kadr_runRuns one command; the result or an error with a hint. project_id is filled in from the chat.
kadr_batchRuns several project commands as one atomic undo step.
kadr_preview_frameRenders a frame and returns it as an image to vision models (metadata only otherwise); the chat shows a thumbnail.
kadr_ui_toastA short progress note in the editor window.

Its system prompt contains the same conventions as Concepts plus the current context: project, playhead, selection, permission mode and today's date. Long chats are summarised automatically; old tool results are shortened and only the last few images stay in context.

How a CLI agent is launched

  • Headless, in its own working folder (by default %TEMP%\kadr-agents\<agent>-<chat>), kept stable per chat so the CLI's own session can be resumed on the next message.
  • Kadr's MCP server is injected for that run only, never into the user's global configuration: by a flag (Claude Code --mcp-config + --strict-mcp-config, Codex -c mcp_servers.kadr.*, Copilot --additional-mcp-config, Qwen --mcp-config), by an environment variable pointing at a temp file (Amp, Cline, OpenCode), or by a project-local file inside the working folder (Gemini CLI, Cursor, Antigravity, Kimi, Crush, Droid).
  • Two transports, one gate. Every run starts its own MCP server inside Kadr (the gateway) on 127.0.0.1 with a random secret path; it asks the permission gate before every call, so approval cards work even for CLIs without a headless permission channel. gateway CLIs connect to it over HTTP; stdio CLIs start kadr-mcp --gateway <url>, a plain bridge to the same gateway that never calls the REST API itself (Kadr only uses a kadr-mcp that supports this mode), so no CLI agent reaches Kadr's tools around the gate. Claude Code and Cline also map their own permission prompts (including shell and file actions) to approval cards.
  • Built-in shell, file and web tools are disabled or denied by default with each CLI's own mechanism. The chat switch Allow actions outside Kadr enables them (still asked unless the chat is in full auto). CLIs that cannot be limited this way (Kimi Code, Warp) start only with that switch on.
  • Keys for a CLI come from the vault and reach it only through its environment — never in arguments, files or events. Every line of its output passes a redactor.
  • Stop ends the whole process tree (on Windows the agent runs in a Job object, so nothing is left behind).

Tool list per agent. Every command as its own tool is about 200 tools and roughly 400 KB of descriptions and schemas sent with each turn, more than some model stacks accept. So CLI agents get the five meta-tools by default (about 4 KB): they search the registry, read a command's documentation, and run commands. kadr_run and kadr_preview_frame are unwrapped before the permission gate, so approval cards name the real command. Claude Code keeps the full list. assistant.settings.set {"cli_tools": {"codex": "full"}} switches one agent (Settings → AI assistant → the agent → Kadr tools), and "" restores its default. A custom agent chooses with tools in its spec.

The permission gate

Every call the assistant makes — through a meta-tool, the gateway or a CLI's own permission prompt — is classified before it runs. The chat's mode decides what needs an approval card:

ClassExamplesask_risky (default)ask_everyfull_auto
Readtimeline.get, preview.frame, *.listrunsrunsruns
Undoable edittimeline.segment.split, text.addrunsasksruns
paidvideogen.generate, tts.speak with a paid voiceasks, with the priceasksasks
deleteproject.delete, removing fonts, presets or providersasksasksruns
overwritean export or caption file over an existing fileasksasksruns
systemupdates, FFmpeg download, API address, render settings, installing CLIsasksasksruns
Outside Kadra CLI's shell, file or web toolasks (if allowed at all)asksruns (if allowed)
secret and blockedsecrets.*, *.keys.*, tts.set_api_key, tts.provider.add, spending.set_limit, any call with a key/token/password argument, the assistant's own non-read-only commandsnever runs — the tool is hidden or refused

The class comes from risk in the command spec (paid, delete, overwrite, system, secret — the same value external agents see as risk in GET /api/v1/commands, x-risk in OpenAPI and a Risk: line in every MCP tool description) plus rules for calls whose risk depends on the arguments (an export that would overwrite an existing file, a cloud voice, a call that carries a key). For paid calls the gate runs the matching <namespace>.estimate to show the cost and, once approved, injects its confirm_token into the call — an agent inside the assistant never handles tokens. “Always for this chat” remembers an approval per command (never for paid calls). Unanswered cards are denied after 10 minutes; a denied action must not be retried.

Drive the assistant from code

# what can power it
curl -s http://127.0.0.1:7777/api/v1/commands/assistant.providers -H "Authorization: Bearer $KADR_TOKEN" -d '{}'
# send a message and wait for the whole turn
curl -s http://127.0.0.1:7777/api/v1/commands/assistant.send -H "Authorization: Bearer $KADR_TOKEN" \
  -d '{"project_id":"prj_1a2b3c4d5e6f","provider":"api:anthropic","text":"Add a title \"Day 1\" for the first 3 seconds","wait":true}'
# answer an approval card (from an assistant.approval_request event)
curl -s http://127.0.0.1:7777/api/v1/commands/assistant.approve -H "Authorization: Bearer $KADR_TOKEN" \
  -d '{"session_id":"ses_0a1b2c3d4e5f","request_id":"perm_1a2b3c4d","decision":"allow"}'
# undo everything the chat did (one undo step)
curl -s http://127.0.0.1:7777/api/v1/commands/assistant.revert -H "Authorization: Bearer $KADR_TOKEN" -d '{"project_id":"prj_1a2b3c4d5e6f","session_id":"ses_0a1b2c3d4e5f"}'
kadrctl run assistant.providers
kadrctl run assistant.send --project_id prj_1a2b3c4d5e6f --provider api:anthropic --text "Add a title \"Day 1\" for the first 3 seconds" --wait
kadrctl run assistant.approve --session_id ses_0a1b2c3d4e5f --request_id perm_1a2b3c4d --decision allow
kadrctl run assistant.revert --project_id prj_1a2b3c4d5e6f --session_id ses_0a1b2c3d4e5f
  • assistant.send returns at once with session_id and run_id (or, with wait, the final answer, usage and cost). Without session_id it starts a new chat; the first message saves the checkpoint for assistant.revert. Attachments: absolute paths, pasted data (data_base64), text, material_id, segment_id or time_us.
  • Live events on the WebSocket (/api/v1/events): assistant.message.delta, assistant.message, assistant.thinking, assistant.tool_call, assistant.tool_result, assistant.approval_request, assistant.approval_resolved, assistant.usage, assistant.status, assistant.error, assistant.done. assistant.session returns a stored chat as the same events, so one reducer renders both.
  • assistant.stop ends a turn; assistant.revert fails with conflict when someone else edited the project since the checkpoint, unless force: true — ask the user first.
  • Edits made by the assistant carry the source assistant in the undo history and in project.changed events.
  • Chats live in the project folder (assistant/sessions/), are never exported and are deleted with the project; assistant.sessions lists them with cost and edit counts.

If you add commands to Kadr

Set Risk on a new command.Spec when it spends money (paid, and offer an <namespace>.estimate that returns a confirm_token), deletes from disk (delete), may overwrite a file outside the project (overwrite), changes the installation or the machine (system) or takes a credential (secret). Ordinary undoable edits need nothing: the assistant runs them freely in the default mode and they can be reverted.
